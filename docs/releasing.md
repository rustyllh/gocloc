# Release verification

Pushing a version tag (`v*.*.*`) starts the release workflow. It does not publish immediately:

1. The reusable **Go** workflow builds and runs unit/integration tests with the race detector on Linux,
   macOS and Windows, using both Go 1.23 and stable. It also checks formatting/imports once.
2. The reusable **Installers** workflow tests Unix installers on Linux/macOS and Windows installers
   under both Windows PowerShell 5.1 and PowerShell 7, using offline release fixtures.
3. Only after both workflows pass, GoReleaser builds all seven supported targets and creates the archives
   and SHA-256 manifest, with publishing disabled.
4. Three native jobs download those artifacts, verify the presence/checksums of all seven archives,
   extract the executable matching their host OS/architecture, check its version, and run the CLI
   integration suite against it (statistics, duplicate modes, worker options, filters, output formats,
   short/long flags, errors and paths). The CLI is **not rebuilt** for these tests.
5. Only after all native jobs pass, a job with `contents: write` publishes the **same archived files**
   as a GitHub Release. Prerelease tags produce prereleases; release notes are generated by GitHub.

A failed prerequisite blocks publication. A passing workflow for another commit is not accepted:
the reusable workflows, packaging and native tests all use the triggering tag's revision.
Artifact-based jobs avoid running the installer against a release that has not been published yet.
The installation tests and packaged-CLI tests are complementary, not a live network installation test.

All architectures are cross-built and checksummed. Runtime smoke tests cover each runner's native
architecture on three operating systems, **not every architecture** (for example i386 is not executed).
The test selects the native archive dynamically, so it does not assume a fixed macOS runner CPU.
Release candidates are retained for seven days if investigation is needed.

Use **Actions → release → Run workflow** to rehearse this pipeline on a branch before tagging.
Manual runs build and verify a snapshot, upload the candidates, and **skip publication**.

## Local checks

```sh
go test -race -tags=integration ./...
sh scripts/test-install.sh
```

On Windows, build `bin/gocloc.exe` and run `scripts/test-install.ps1 -BinaryPath ./bin/gocloc.exe`
under both PowerShell versions. These tests use temporary directories; they do not upgrade your installation.

With an unpacked candidate artifact directory (all archives and the manifest), test the native release
binary on macOS/Linux as follows; use equivalent environment variables in PowerShell on Windows:

```sh
GOCLOC_RELEASE_DIR=/path/to/release-candidates GOCLOC_RELEASE_VERSION=vX.Y.Z go test -tags=integration ./cmd/gocloc -run '^TestCLIIntegration$' -count=1 -v
```

Without these environment variables the integration suite builds the CLI locally as before.
Performance reports are documented in [benchmarking.md](benchmarking.md); noisy CI timings are not
a release gate. Existing published versions are unaffected by workflow changes.
