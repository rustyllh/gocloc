# Release verification

Pushing a version tag (`v*.*.*`) starts the release workflow. It does not publish immediately:

1. The reusable **Go** workflow builds and runs unit/integration tests with the race detector on Linux,
   macOS and Windows, using the latest stable Go release. It also checks formatting/imports once on Linux.
2. The reusable **Installers** workflow tests Unix installers on Linux/macOS and Windows installers
   under both Windows PowerShell 5.1 and PowerShell 7, using offline release fixtures.
3. Only after both workflows pass, GoReleaser builds all seven supported targets and creates the archives
   and SHA-256 manifest, with publishing disabled.
4. Three native jobs download those artifacts, verify the presence/checksums of all seven archives,
   extract the executable matching their host OS/architecture, check its version, and run the CLI
   integration suite against it (statistics, duplicate modes, worker options, filters, output formats,
   short/long flags, errors and paths). The CLI is **not rebuilt** for these tests.
5. A Docker job wraps the checksummed Linux `amd64` and `arm64` executables in minimal images,
   tests their platform, version, JSON output and duplicate modes (ARM64 uses QEMU), then publishes
   both images by digest and a multi-platform manifest to Docker Hub on tag pushes. The binaries are not rebuilt.
6. Only after the native and Docker jobs pass, a job with `contents: write` publishes the **same archived files**
   as a GitHub Release. Prerelease tags produce prereleases; release notes are generated by GitHub.

A failed prerequisite blocks publication. A passing workflow for another commit is not accepted:
the reusable workflows, packaging and native tests all use the triggering tag's revision.
Artifact-based jobs avoid running the installer against a release that has not been published yet.
The installation tests and packaged-CLI tests are complementary, not a live network installation test.

All binary architectures are cross-built and checksummed. Archive smoke tests cover each runner's native
architecture on three operating systems, **not every architecture** (for example i386 is not executed).
The test selects the native archive dynamically, so it does not assume a fixed macOS runner CPU.
Release candidates are retained for seven days if investigation is needed.

Use **Actions → release → Run workflow** to rehearse this pipeline on a branch before tagging.
Manual runs build and verify a snapshot (including Docker images), upload the binary candidates,
and **skip both Docker Hub and GitHub Release publication**. They do not need Docker Hub credentials.

## Docker Hub setup

Before pushing the first Docker-enabled release tag:

1. Create the `rustyllh/gocloc` repository on Docker Hub with public visibility if it does not exist.
2. Create a Docker Hub access token with permission to read and write this repository; delete permission is not needed.
3. In the GitHub repository's **Settings → Secrets and variables → Actions**, add repository secrets:
   - `DOCKERHUB_USERNAME`: `rustyllh` (or an authorized account with write access to the namespace).
   - `DOCKERHUB_TOKEN`: the access token, not an account password.

Do not commit credentials or place them in workflow files. Missing or invalid credentials fail the Docker job
and block the final GitHub Release publication. Pull requests and branch pushes never push images.
Only new version tags containing this workflow enable Docker publishing; do not move an existing release tag.

Image tags in `docker.io/rustyllh/gocloc`:

- `vX.Y.Z`: a manifest for `linux/amd64` and `linux/arm64`.
- `latest`: updated by stable version tags only, never by a prerelease such as `vX.Y.Z-rc.1`.

No architecture-suffixed tags are published. The tested local images are exported with `docker image save`
and uploaded directly to digest references using pinned `crane` v0.22.1, which reads the Docker login credentials.
The two public tags reference a multi-platform manifest, and Docker automatically selects the correct platform.
Prereleases only publish their version tag. Historical version tags and any architecture tags created by older
workflows are not deleted automatically.

Docker Hub publication happens before GitHub Release publication; the two services are not transactional.
If a push or the final GitHub publication fails, some Docker tags may already exist. Fix the cause and rerun
the failed jobs for the same revision rather than moving the Git tag. Existing images are not deleted.

The Dockerfile's default target builds from source with the latest Go 1.x image; `GO_VERSION` can pin it.
Its `release` target only copies supplied binaries, preserving GoReleaser's version/commit information.
Both targets use a `scratch` runtime containing the executable and license, without a shell or UPX.

## Local checks

```sh
go test -race -tags=integration ./...
sh scripts/test-install.sh
bash scripts/test-docker-release.sh
```

The last command checks build and publication success/failure paths with fake Docker and crane commands;
it does not replace the real two-architecture image tests in the release workflow.

With Docker running, Buildx, `jq`, and all release archives/checksums downloaded:

```sh
bash scripts/build-docker-release.sh /path/to/release-candidates X.Y.Z
```

Use the packaged version without the Git tag's `v` prefix. This builds and tests local images named
`gocloc-release-candidate:amd64` and `gocloc-release-candidate:arm64`; it never logs in or pushes.
Docker must support executing both Linux architectures (Docker Desktop provides emulation; CI sets up QEMU).
Use the workflow's manual run when the local Docker engine or emulation is unavailable.

On Windows, build `bin/gocloc.exe` and run `scripts/test-install.ps1 -BinaryPath ./bin/gocloc.exe`
under both PowerShell versions. These tests use temporary directories; they do not upgrade your installation.

With an unpacked candidate artifact directory (all archives and the manifest), test the native release
binary on macOS/Linux as follows; use equivalent environment variables in PowerShell on Windows:

```sh
GOCLOC_RELEASE_DIR=/path/to/release-candidates GOCLOC_RELEASE_VERSION=vX.Y.Z go test -tags=integration ./cmd/gocloc -run '^TestCLIIntegration$' -count=1 -v
```

Without these environment variables the integration suite builds the CLI locally as before.
Performance reports are documented in [benchmarking.md](benchmarking.md); noisy CI timings are not
a release gate. Existing published versions are unaffected by workflow changes.
